# release-kit

Versioning and release notes from change fragments, built for AI agents and CI.

- Agents write one Markdown fragment per user-visible change in `.release/changes/`.
- `check` validates fragments, the PR title, and whether a fragment is required.
- `plan` computes the next version from the fragments and explains why; `apply` writes it.
- Every command supports `--json`, never prompts, and exits with a stable code.

Requires Node.js 20 or later and git.

## Quick start

```sh
npm install -D @coszone/release-kit      # or: npx @coszone/release-kit <command>

release-kit init --preset library --agents
release-kit add --kind feat --field docs=updated --body "Topics can be created from YAML."
release-kit check --base origin/main --pr-title "feat: create topics from YAML"
release-kit plan
release-kit preview --channel alpha
release-kit apply --dry-run
release-kit apply
```

`init --agents` also writes a marked block into `AGENTS.md` and an Agent Skill at `skills/release-kit/SKILL.md`. Re-running `init` changes nothing.

## Fragments

```md
---
kind: breaking
docs: updated
pr: 128
---

`topics` in `harness.yaml` are now declared per project.

## Upgrade

Move `topics.<name>` to `projects.<name>.topic`.
```

- `kind` maps to a version level in `release-kit.yaml`. Kinds that bump major need an `## Upgrade` (or `## 升级`) section.
- Custom fields such as `docs` are declared under `fields` with an enum and the kinds that require them.
- Write the body for users. `check` warns about file paths and code identifiers.

## Commands

| Command | Purpose | Writes |
|---|---|---|
| `init [--preset library\|web\|electron] [--agents]` | Create config and fragment directory | yes |
| `add --kind <k> (--body <text> \| --body-file <path\|->) [--id] [--pr] [--field k=v]` | Create a fragment; same id and content is a no-op | yes |
| `check [--base <ref>] [--pr-title <title>]` | Validate fragments, PR title, required fragments, body rules | no |
| `plan [--channel <c>]` | Next version, deciding fragments, 0.x adjustment | no |
| `preview --channel <c> [--write-version]` | Next `X.Y.Z-<c>.N` from git tags plus rendered notes | only with `--write-version` |
| `apply [--version <v>] [--dry-run]` | Write version files and notes, delete consumed fragments | yes |
| `describe` | Commands, options, exit codes, issue codes, config and fragment JSON Schemas | no |

Global options: `--json`, `--cwd <dir>`, `--help`.

## Versioning rules

- The highest bump among pending fragments wins.
- While the version is `0.x`, major-level changes become `versioning.pre1.breaking` (default `minor`) and the output sets `pre1Adjusted: true`. Reaching `1.0.0` requires `apply --version 1.0.0`.
- Prerelease numbers continue from existing tags (`v0.15.0-alpha.1` → `v0.15.0-alpha.2`). Without any matching tags `preview` exits with code 3 and suggests `git fetch --tags`.
- `apply` does not commit or tag; it prints the commands in `nextSteps`. If a previous run was interrupted after writing the version files and notes, `apply` only deletes the leftover fragments (`resumed: true`).

## PR numbers

- `add` fills a missing `pr` from `RELEASE_KIT_PR`, or from `GITHUB_REF` when it is `refs/pull/<n>/merge`.
- `check` reports that number as `checked.pr`, and lists the PR's fragments without a `pr` in `checked.prFill`.
- `apply` fills any remaining gaps from the first-parent commit that added the fragment, e.g. a squash subject ending in `(#12)`. Set `notes.prFromGit: false` to turn this off. No network calls are made.

## Machine interface

```json
{
  "schemaVersion": 1,
  "ok": false,
  "command": "check",
  "issues": [
    {
      "code": "RK012",
      "severity": "error",
      "file": ".release/changes/save-feedback.md",
      "line": 2,
      "message": "PR title type is \"feat\", but fragment kind is \"fix\"",
      "fix": "Change the kind to feat, or rename the PR to \"fix: …\""
    }
  ]
}
```

| Exit code | Meaning |
|---|---|
| 0 | Success (warnings may be present) |
| 1 | Validation failed |
| 2 | Usage error |
| 3 | Environment error (missing config, git, tags, or version file) |

Run `release-kit describe --json` for the full reference. The config schema is published at `https://unpkg.com/@coszone/release-kit/schema/config.json`.

## Configuration

`release-kit.yaml` (generated by `init`):

```yaml
# yaml-language-server: $schema=https://unpkg.com/@coszone/release-kit/schema/config.json
version: 1
changes: .release/changes
notes:
  dir: docs/releases
  file: v{version}.md
  template: default-en # default-en | default-zh | path to a Mustache-style template
versioning:
  files:
    - { path: package.json, key: version }
  tag: v{version}
  pre1: { breaking: minor }
  channels:
    alpha: { strategy: tag-only }
kinds:
  breaking: { bump: major, require: [upgrade] }
  feat: { bump: minor }
  fix: { bump: patch }
  perf: { bump: patch }
  internal: { bump: none, notes: false }
fields:
  docs: { enum: [updated, not-needed], requiredFor: [feat, breaking] }
checks:
  requireChange:
    paths: ["src/**"]
    exemptTitleTypes: [docs, chore, test, ci, build, style]
  prTitle: conventional
  body:
    maxLength: 400
    discourage: ["\\bsrc/", "\\.[jt]sx?\\b"]
```
